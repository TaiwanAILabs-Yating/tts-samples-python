# TTS segment 尾端雜音清理（試聽、下載、合併皆無爆音）

> 日期：2026-09-15
> Branch: `feat/segment-tail-artifact-clean`

## 問題

分析 2,821 個 TTS API 原始輸出（中文 1,412 + 台語 1,409，結尾靜音 token 開啟）：

- 約 **8%（230 個）結尾有明顯爆音**，中文、台語比例相同
- 形狀不是「波形未歸零」，而是**模型在最後約 12ms 生成的削波雜音**（衝到 0dBFS），前面通常已經安靜
- 雜音會同時影響：segment 試聽、segment 下載、整句結尾，以及**句子中間的接點**
  （silenceremove 把雜音當成聲音保留，連前面的靜音也修不掉，再被 crossfade 帶進接點；
  25 組實測接點峰值中位數 -27.9dB，清理後 -43.3dB）

淡出無效：10ms 淡出（FFmpeg 與 JS 結果逐樣本相同）只把峰值從 -0.1dB 壓到 -4.8dB，99% 仍明顯；
30ms 淡出仍有 97%。必須**切除**雜音。

## 做法

`src/utils/segment-tail.ts` 的 `cleanSegmentTail()`，純 JS 處理 16-bit PCM WAV（不經 FFmpeg，每段約 0.35ms）：

| 規則 | 條件 | 用途 |
|------|------|------|
| 1 | 結尾連續 > -45dB 的區段 ≤ 30ms，且前面有 ≥ 5ms 安靜 | 主要的尾端雜音（安靜後暴衝） |
| 2 | 結尾 > -20dB 的區段 ≤ 30ms、峰值 ≥ -10dB、比前 20ms 大聲 ≥ 15dB（多切 2ms 上升邊緣） | 雜音前是輕微尾音而非靜音 |
| 3 | **僅在規則 1 或 2 成立時**：往回 60ms 內，前有 ≥ 3ms 安靜、> -30dB 持續 ≤ 15ms、大聲 ≥ 15dB 的喀聲（多切 2ms） | 主雜音前的較小前置喀聲 |
| — | 切除後一律淡出最後 10ms | 讓播放停止時不會有階梯 |

- 規則 3 限定在已確認有雜音的 segment，避免誤判字尾子音（英文 t、k 等）
- 門檻都落在「附近數值切除結果完全相同」的穩定區間（規則 2：跳升 10～15dB × 峰值 -10～-15dB 結果相同）
- 語音本身在結尾被截斷（講到最後仍 -12～-20dB）不切除，只淡出 — 模型截掉的聲音後處理無法補回

### 套用位置：TTS 音檔的唯一入口

`tts-orchestrator.ts` 的 `acceptSegmentAudio()`：TTS 回傳後立刻清理再寫入 `segment.audio`
（生成、重生單段、重生整句三條路徑共用）。因此：

- segment 試聽、segment 下載、合併、重生歷史紀錄**自動全部使用清理後音檔**，不會漏掉路徑
- `duration` / `trimmedDuration` 以清理後音檔量測（雜音會讓修剪長度差到 0.25s 以上）
- 句子試聽（波形播放器）、句子下載、ZIP 皆來自清理後的 segment 合併結果
- `segment.tailCutMs` 記錄切除毫秒數，並寫入 `metadata.json` 的 `segments[].tailCutMs`
- 取捨：App 內不再保留原始 TTS 音檔（App 原本就沒有使用或下載原檔的地方）

## 驗證

| 項目 | 結果 |
|------|------|
| 資料集（2,821 檔） | 爆音檔 230 個中切除 201 個（其餘多為語音本身被截斷，只淡出）；乾淨檔 778 個僅 1 個被切 2ms 底噪（聽不出）；全部共切除 313 個 |
| 試聽（人工） | 第一～四版逐版試聽確認；1187、0353、0264、1129 等邊界案例確認無殘留爆音、未切到字 |
| 移植一致性 | TS 版與試聽確認的第四版 JS，2,824 個檔案輸出**逐位元組相同** |
| 單元測試 | 規則 1／2／3、未確認雜音時不找喀聲、截斷語音只淡出、>30ms 不切、已靜音結尾不變、串流 header、多聲道、非 WAV／非 16-bit 原樣返回 |
| E2E（真實 UI，網路全攔截） | Setup → Create & Generate，TTS 回傳真實爆音檔：segment 試聽與下載與預期清理結果逐位元組相同；ZIP 整句結尾與清理後最後一段一致（原檔 -0.6dB／相鄰差 0.646 → -25.1dB／0.016）；metadata 帶 `tailCutMs` |

## 限制

- 規則以中文、台語資料調校，**英文、日文、韓文尚未驗證**
- 本次變更前已 Approve 存在 IndexedDB 的整句音檔不會被回溯清理，重新生成即可
- 根本原因在模型端（疑似與 `<|sil_200ms|>` 結尾處理有關），建議回報模型團隊
